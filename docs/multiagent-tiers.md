# Мультиагентный контур: три зоны (концепт, не реализовано)

Статус: **концепт**, согласован по смыслу с владельцем 2026-11-05. Ничего не реализовано.
Цель — разделить не «агентов», а **зоны доверия** по типу контента, который проходит через канал.

## Принцип

Уровень привилегий определяется не удобством, а тем, какой контент проходит через канал.
Один root-инстанс = один канал (Telegram владельца). Всё остальное — без root.

## Зоны

**Зона 1 — владелец, прямой канал (как сейчас).**
Hermes на хосте, root, yolo, полный харнесс. Единственный root-инстанс.

**Зона 2 — полу-доверенная (OWUI-чат, если в него попадает внешний контент).**
Второй инстанс **без root**. Оправдан не удобством, а грязным контентом: ссылки, PDF, ответы веба.
Root-операции только через эскалацию в зону 1.
Если в OWUI ходят только собственные формулировки владельца — отдельный инстанс не нужен,
это был бы второй root-канал без пользы.

**Зона 3 — чужие пользователи (гости).**
Один инстанс на всех (не по инстансу на пользователя), изоляция по сессиям внутри процесса.
Терминал — песочница, ноль sudo.

## Эскалация болталка → админ (или зона 2 → зона 1)

Наивная схема «пишет свободным текстом, админ выполняет» — дыра: prompt injection в контенте
болталки превращается в root-команду. Правильная форма:

- **Заявка типизирована**: `{action, target, params, reason, budget}` — не «прими команду».
- **Allowlist в коде, fail-closed** (`pre_tool_call` хук). Сложное («почему диск кончается») —
  отдельный тип «задача», а не заявка, и тоже с лимитом.
- **Скилл-валидатор** — третий слой, только для нечёткого; умеет **только отказывать**,
  не расширять права.
- **Сообщение болталки не может приходить как user-turn** — только как результат инструмента,
  уже провалидированный по схеме.
- **Ответ структурный**: `{ok, exit_code, artifact_path, summary}` + путь к сырому артефакту,
  чтобы не было телефонного телефона при пересказе.
- **Аутентификация токеном**, локальность — не аутентификация.
- **Журнал** эскалаций: кто, что, зачем, что вернули.
- **Бюджет и таймаут** на заявку (защита от циклов).

## Где проходит граница прав (жёсткие правила)

- `docker.sock` = root-equivalent. При мультиюзере он **убирается** из OWUI/open-terminal,
  а не «компенсируется харнессом». Харнесс спасает от глупости, не от злого умысла.
- «Список sudo-команд, которые точно не уебут сервер» — иллюзия: `systemctl edit`, `journalctl`,
  любой `docker`, `sudo tee`/`sudo cat` на симлинке дают произвольную запись/чтение.
  Для гостей — **ноль sudo**, вместо него узкий CLI-враппер с фиксированными глаголами
  (`ps`, `logs`, `inspect`, `restart <whitelist>`), валидирующий аргументы.
- **Утечка через скиллы — самое вероятное место утечки.** В скиллах лежат пути, IP, имена
  сервисов, схемы бэкапов. Гостевой инстанс обязан иметь свой пустой `skills/` и свой
  `HERMES_HOME`, иначе вежливо расскажет гостю инфраструктуру.

## Физическое разведение (минимум)

- разные системные юзеры и systemd-юниты (`hermes` / `hermes-guest`), разные `HERMES_HOME`
- `NoNewPrivileges=yes`, `ProtectSystem=strict`, без `/root`, без `docker.sock`
- разные боты/токены, разные наборы скиллов, разные бюджеты прогона
- журнал эскалаций и лимиты прогона на зонах 2–3

## Открытые вопросы

1. Транспорт эскалации: Hermes webhook против Redis/RabbitMQ-очереди (оба уже есть в стеке).
2. Кто исполняет заявку: хук+CLI, или агентский прогон в зоне 1 (сейчас — второе для «задач»,
   первое для операций из allowlist).
3. Общая база конфигов/скиллов, чтобы три инстанса не разъехались (git + тонкий слой различий).
4. Бэкап и обновление всех инстансов — иначе через месяц три разные версии.
